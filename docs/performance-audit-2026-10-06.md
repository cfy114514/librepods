## 其他性能与稳定性修复

- AACP 在派发前检查各类型包的最小长度；音频源、连接设备列表、设备信息、密钥解析改用准确边界。非法包不会因这些解析错误结束整条收包循环；完整设备列表解析成功后才替换状态。
- AACP 写 socket 使用 output 锁，防止并发包交错；删除每个控制回复格式化整张状态表及未使用的三个 EQ FloatBuffer。
- 电量、佩戴、ANC、对话通知直接比较字节前缀，删除重复字符串/十六进制格式化。ANC 名称由当前状态动态计算。
- 控制状态读写使用防御性副本和同步快照，Repository 不再遍历正在被收包线程修改的列表。
- ATT 缓存属于各 ReaderSession，断连和旧 reader 不会重新填充新连接缓存；通知更新缓存，只有确认成功的写入才保存数据。
- ATT Error Response 按请求 opcode 匹配，立即解除等待。超时或取消后关闭该 ATT 会话，避免无事务编号的迟到回复被下一个请求误用；AACP 保持独立。**这意味着真正超时后，通透/听力等 ATT 功能需重新连接耳机才能恢复。**
- 停止旧 ATT reader 时验证 socket 身份；服务销毁和主动断连清理 reader；ViewModel 待发送写入捕获服务、socket 和数据，取消/替换时不会发送到后续连接。订阅失败不会永久标为已订阅。
- BLE 旧 callback 在扫描重启/停止后失效，即使 stopScan 因权限变化失败也不会继续更新状态；批次选择每个地址最新时间戳的广播。
- BLE 超时使用 elapsedRealtime，避免修改系统时间导致设备错误消失或长期不消失；充电标志变化触发电量更新。充电盒无效值不再借旧值冒充本次广播的实时读数，旧值只进入单独的带时间历史展示。
- 每次连接/充电状态转换才调用音频 profile 操作，重复电量报告不会重复连接/断开；断连清理转换记录。HeadTracking 采样和校准重置串行化，完成校准后清空样本。

## 后续持续优化

- 用户确认第五代非 Pro。Apple 功能对照及新增实时聆听、相机遥控的边界见 [功能对照](airpods-5-parity-2026-10-06.md)。不把官方规格、界面开关或 JVM 测试写成 Apple 真机功能完全等价。
- AACP 读取不再等待前 1 秒启动请求发送完成，分离为同一 reader 生命周期中的启动子任务；reader 结束时取消其延迟重发。删除服务启动时的头部跟踪校准，防止启动设置页为了采样去请求接管音频，也避免 5 秒后误停用户主动开启的跟踪。通话手势不再重复启动并重置校准。
- BLE 状态表改用并发表，避免后台读取最近状态时遍历正在修改的普通 Map。电量刷新只读取一个快照，缺失值交给已有无效电量处理，避免重复六次查找及把未知状态写成 0%。
- 不完整的连接广播不再强制解包崩溃；异步连接捕获广播中的设备，避免全局 device 替换后连接错误的目标。未知或过期的耳柄动作偏好使用当前默认动作，避免 `valueOf`/`!!` 导致启动或配置监听崩溃。
- [#700](https://github.com/librepods-org/librepods/issues/700) 是 Android 17、Pro 3、自定义 ROM 的报告，不能直接认定影响用户的 AirPods 5。原生代码此前任何系统都把 `l2c_fcr_chk_chan_modes` 结果强制改为 1；现在 API 37 及以后默认保留原始结果，API 36 及以前保留旧补丁。Xposed 设置可在 API 37 及以后强制回退旧补丁，需重启蓝牙。原生加载路径自身执行版本策略，不只依赖 Kotlin 回调；删除热路径重复日志。编译期断言检查版本边界和强制回退。**这是可回退的兼容调整，报告的根因及新行为均需真机验收。**
- [#742](https://github.com/librepods-org/librepods/issues/742) 要求断连后保留带时间标识的历史电量，属于可用性改进；已增加按保存耳机地址隔离的持久化历史电量、各部件真实观测时间及 1/7/30 天过期策略。断连页面和组件使用明确的历史标识，未知与真实 0% 区分。无效包不刷新历史时间，不把历史充电标志用于实时状态或音频策略。BLE 只有密钥所属地址已验证时才写历史，旧版本没有密钥归属记录的用户需重新连接获取密钥。

后续验证采用相同串行命令；签名证书保持一致。该早期阶段没有连接的 ADB 设备；后续隔离模拟器安装核验见续轮记录。实体麦克风路由、相机快门、多设备音频及原生补丁运行仍未验收。

## 电量历史、手势与音频归属续轮

- 历史电量同值观测只每 30 秒持久化，值/设备变化立即保存，断连和服务销毁刷新；十万次同值观测的节流测试检查写入次数。当前组件继续使用实时读数，缺失部件才显示有效历史，并附星号及更新时间。历史不会写入蓝牙系统元数据。
- 每个 BLE 广播仍更新观测新鲜度，但只有电量/充电/所属耳机变化才触发组件和通知工作；随机 BLE 地址、开盖和时间戳变化不再重复电量 IPC。
- 头部手势高频采样、平滑、峰值和周期窗口改用固定容量的原生 DoubleArray 环形缓冲，删除列表头部移动和临时尾部集合。与原算法对照一万组固定随机输入，样本顺序、均值、绝对均值和方差数值一致；一百万次采样验证容量有界。阈值、轴映射与置信权重没有根据无日志 issue 重调。
- 音频归属以每个 profile 的实际连接与 `setConnectionPolicy` 接受结果为依据；只释放已连接的 profile。失败的策略恢复保留记录；控制 socket 掉线保留已设置 FORBIDDEN 的记录并取消旧回调。用户断开、另一个主机接管或更换耳机取消恢复；实际新连接、手动重连或明确启用的接管才重新授权。
- 首条被动通知不能取消手动连接。未执行的释放在用户重新戴入时失效。播放监听仅覆盖一次具体 A2DP 恢复，拒绝连接、取消、旧 socket 或 10 秒超时均移除；旧清理不能移除新监听。profile 事务不持有 MediaController 锁，避免与媒体回调中接管形成逆序锁。
- 取消所选设备的连接尝试时不再发误导的“连接超时”通知。BLE 触发的连接交给服务后台任务，扫描回调不等待蓝牙连接或 root 地址查询。SDP 补查询仅对已确认本地音频连接、尚缺 UUID 的设备发起，避免破坏首次发现功能。

**音频策略边界：** FORBIDDEN 属于系统持久状态，释放记录属于当前服务进程。若 root/system 安装在释放后被强制杀进程，或另一个主机接管后策略仍为 FORBIDDEN，需从应用手动重连/接管或在系统蓝牙设置重新允许相应音频。没有凭历史记录推断另一个主机当前是否在使用耳机。当前未连接真机，不能宣称 #784 在用户固件与 Android 上已经完全解决。

Android 依据：[A2DP 连接状态广播](https://developer.android.com/reference/android/bluetooth/BluetoothA2dp)、[BluetoothProfile 的目标设备连接状态](https://developer.android.com/reference/android/bluetooth/BluetoothProfile)、[RemoteViews 尺寸 API](https://developer.android.com/reference/android/widget/RemoteViews)。

- 佩戴广播使用当前包的状态，修正原来发送上一条状态的问题。另一个主机持有音频后，佩戴通知仍更新显示，但不自动播放/暂停本机媒体；有 A2DP 恢复等待时，戴入单耳也等待连接确认。
- 新连接和断连使前一条连接的电量失效。蓝牙电量元数据使用一次完整快照，只写当前有效读数，避免无效/断连值和旧充电标志被当成实时更新。

- 特权系统电量广播也排除旧连接、无效值和仅充电盒读数，真实 0% 保持为 0%。Apple HFP 电量事件只有 10% 分档，普通精确百分比事件仍携带原始有效百分比，二者不能混用字段。依据 [AOSP RemoteDevices 的 Apple 电量解析](https://android.googlesource.com/platform/packages/apps/Bluetooth/+/28ae770dc37d7ab2e3c150cfacf197e7651cfa03/src/com/android/bluetooth/btservice/RemoteDevices.java)。

## 桌面组件刷新续轮

组件刷新以前在蓝牙收包线程或主线程直接执行 AppWidgetManager IPC。现在调用者只提交一个 dirty 标记，由所属服务的 IO worker 在 100 ms 合并窗口后读取最新状态；最多一个正在执行的任务和一个待刷新标记。窗口内请求不会推迟截止时间，执行期间的新请求触发一次后续更新，服务销毁取消等待中的任务。临时 host/权限异常不阻断后续刷新。发布前再次检查所选耳机、控制 socket 和服务身份。每轮增加 100 ms 合并等待，系统调度和 IPC 耗时另计；正在进行的一次系统 IPC 无法主动撤回。

手机电池广播仅在显示百分比或充电图标变化时提交刷新；温度、电压等变化不会重复刷新。有效 0% 与未知读数分开，重新注册 receiver 后首条 sticky 状态仍会刷新。手机电量显示开关只更新组件，不再额外写耳机元数据或发耳机电量广播。

隔离 API 36 上使用真实 AppWidgetHost、BatteryWidget provider 和 AirPodsService，两个版本均为同证书 FOSS Release。100 次请求：旧版宿主收到 100 次更新，请求过程主线程用时 195 ms；新版收到 1 次，毫秒记录为 0（不能解释为完全零开销）。真实 BatteryService 强制发送的 20 次仅温度变化广播产生 0 次宿主更新；百分比变化仍送达。没有伪造耳机读数，该计数不证明实体手机耗电比例或多组件负载结论。

组件续轮 Release（SHA-256 `FB07584C381756E97E5B98E8A800548EADD1B9CA4E6AE233CAFBAF94AEE0ECB3`）安装哈希回读一致，单次冷启动 1401 ms，无 AndroidRuntime 错误。测试宿主删除、临时绑定授权撤销、测试工具卸载，模拟器电池状态 reset，应用与隔离模拟器停止。证据在 `android/build/widget-probe/` 和 `android/build/avd/widget-runtime-validation.json`。新增 8 项回归覆盖十万次请求、执行期间跟进、停止和替换、临时失败、手机电量边界与规模转换。

## 设置写入与辅助设置页续轮

ViewModel 的控制命令、三段 EQ 和动态充电设置不再在主线程写 L2CAP。每个 ViewModel 服务绑定拥有独立 IO worker，固定已知设置键空间，每个键最多保留一个最新待写值，不同键按入队顺序串行处理。三段 EQ 保存完整最新配置，合并不会丢掉启用状态。队列数据防御性复制，ViewModel 销毁或替换服务取消旧队列；原连接断开后待写设置不会迁移到新连接。界面仍显示用户草稿，设备实际是否应用需要回复和真机回读确认。

AACP 写入捕获原 socket，在获取该输出流写锁后再次检查连接、设备、服务和队列身份，避免等待写锁期间改写另一条连接。输出保持整包串行；失败、无连接或已退休写入不再提前污染控制缓存。Release 删除发送包的调试格式化。

## 睡眠定时器归属与界面刷新续轮

旧闹钟只读取全局结束时间和模式，未记录目标耳机；替换任务后的旧投递可能读到新任务。无服务时直接启动服务并发送模式命令，控制 socket 尚未建立时命令会丢失。现在每个任务保存独立 UUID、规范化耳机地址、模式、墙钟/单调时钟截止时间和系统 boot counter，PendingIntent 的 data 携带 UUID。接收器和服务入口拒绝取消、替换或未提供身份的旧投递；输出锁内再次检查任务、所选耳机、控制 socket 与服务归属。成功写入只清理同一任务，迟到完成不能清除新任务。Bluetooth 写入通过所属 IO worker，最多一个正在执行的任务和一个待处理标记，不在广播主线程写入。

同一次开机优先使用 ELAPSED_REALTIME_WAKEUP，手动改系统时间不改变剩余时长；TIME_SET 更新保存的墙钟截止时间供后续重启恢复。boot counter 不可用时回退 RTC。由启动计数或开机广播确认重启后，尚未到期的任务按墙钟重建单调截止时间；已到期或已进入补执行窗口的任务不回放。若计数不可用且开机广播也未投递，无法可靠识别跨重启记录，此组合尚无保证。升级时旧记录没有原始耳机身份，因此取消，不推断当前耳机就是原目标。更换所选耳机也取消任务。取消/替换时清理闹钟与 PendingIntent。

到期后保留 30 秒补执行窗口，窗口从实际接收定时投递（或已到期后的合法控制连接就绪）开始；重复检查不延长窗口。等待时界面显示等待连接，可取消。只在既有控制连接准备完成后重试，不为定时器额外接管音频。过期后即使清理闹钟被系统延迟，写入检查也会拒绝补执行。原有 setAndAllowWhileIdle 的非精确调度保留，Android 省电策略可能延后闹钟，未增加精确闹钟权限；系统拒绝后台启动服务时只保留短期等待状态，不保证后台从零启动一定成功。成功写入表示手机端发送成功，仍需实体耳机模式回读证明应用成功。

界面按显示分钟的边界刷新，生命周期 STARTED 才运行；前后台切换时重新读取持久状态，偏好改变后刷新。纯状态回归验证整小时为 60 次刷新，而旧固定每秒循环理论上为 3600 次；不是实机 CPU、耗电或帧率测量。

## 听音模式能力、选择器与组件性能续轮

## EQ 缓存与断线界面续轮

## AACP 收包代际与断开归属续轮

服务以前在 read 返回后检查当前 socket，再进入 AACP 解析。断线重置可以发生在检查与缓存保存之间，旧控制包、EQ、音频源或设备列表随后重新填入状态；部分服务回调也没有来源检查。现在每次控制连接发布前清理 AACP 状态并取得代际标记，reader 带着该标记及当前 socket/所选设备条件进入解析；所有可变缓存提交在管理器同步锁内再次检查代际及来源。断线或服务销毁使旧标记失效。控制观察者分别获得数组副本，重置中止剩余旧代际观察者；各 typed callback 分发前再次检查有效性。附近设备提示、头部跟踪、耳柄动作、连接列表和 EQ 广播补上实际 packetSourceSocket / peer 检查。

## 媒体信息发送和延迟接管任务的归属（续轮）

播放回调以前在主线程直接构造并发送媒体信息。现在由服务的 IO 队列处理，一个正在执行的任务之外最多保留一个最新待发状态；构造数据包和写 socket 都不在主线程执行。请求捕获原控制 socket、本机 MAC 和音频归属代际，写入前重新检查服务、所选耳机、原 socket、本机 MAC 和归属；关闭服务会清空待发项。已进入输出流写入的操作不能撤回，不据此声称消除所有断连竞争。

## 接管命令批次与排队请求的状态代际（续轮）

接管入口以前在播放/通话回调的线程同步发送多条命令，每条命令再次读取全局 socket。现在入口只捕获请求并提交给服务所属 IO 队列，同类保留最新值，五类请求最多五个待发项，另外允许一个正在执行的任务。数据包构造、VendorID 偏好查询和 Bluetooth 写入在 IO 执行。没有控制连接时，主连接的超时不再阻挡请求队列；找到正确配对目标并获得条件授权后，先暂停扬声器播放再发起音频连接。

每个已有连接的请求捕获原 socket、所选 MAC、本机 MAC、服务接管代际和 AACP 状态代际。命令批次再捕获一份主机列表，规范化、跳过无效地址并去重，保留 OWNS_CONNECTION → 媒体信息 → 普通接管 UI → 各其他主机的 Hijackv2 顺序。反向接管只发送对应的反向批次，避免再落入普通 Hijack 分支。每条命令使用原 socket，失败或过期即停止，最后一个写入之后再验证代际，过期批次不进入音频授权。未更改私有协议字段或添加推测报文。

手动重连、反向接管和明确的头部跟踪请求与自动接管开关分开判断；手动操作可以在自动接管关闭时请求连接。正常接管仍受 VendorID 条件约束，自动接管不会忽略开关。条件音频授权不会重新选择旧耳机；晚到的 profile 回调也要再次检查请求。接管弹窗在主线程实际显示时重检目标和代际；延迟播放/头部跟踪重检音频、连接与 AACP 代际，用户停止跟踪后不会由旧恢复任务重新启动。

运行验证发现中间版本只绑定正在执行的批次代际，排队请求仍可能在 AACP 重置后重新执行。最终将入队请求也绑定代际，并对媒体信息队列补上同样检查。检查中特意重置并重新填入有效主机列表，避免仅因空列表让测试误判为已修复。没有控制连接的请求允许为同一所选耳机建立新控制会话；已有控制连接的请求不能借用替换连接。

## 音频 profile 回调与接收器生命周期（续轮）

[Android API 文档](https://developer.android.com/reference/android/bluetooth/BluetoothAdapter#getProfileProxy(android.content.Context,%20android.bluetooth.BluetoothProfile.ServiceListener,%20int)) 明确 profile ServiceListener 在应用主 looper 调用。本地以前在该回调内同步查询连接状态、设置连接策略、请求连接并关闭 proxy。现在获取请求在服务 IO scope 执行，回调只交付资源和操作，实际操作与 proxy 释放在 IO。每个已回调资源由 AsyncResourceOperation 跟踪，未开始就取消会跳过操作；同步操作正在执行时，等执行结束再释放，避免关闭正在使用的 proxy。清理不依赖已取消的服务 job；失败、类型不符、过期和服务停止后的已到达回调都会安排释放。

操作绑定服务接管代际，线程局部校验随同步操作设置/移除。平台查询返回之后，在暂停媒体、请求 SDP、设置断开策略及请求连接之前重新检查归属。发现连接设备后的服务/UI 发布交回 Main，携带原回调有效性，避免旧查询重新选中旧目标。

A2DP 自动恢复观察改为原子 watch，含 receiver、profile 凭据、AACP 代际及所属超时任务；旧 receiver 或超时不能移除替换 watch。IO 先注册再请求 connect。DeferredRegistration 处理注册尚未返回就取消的情况，返回后的注册仍被撤销一次；失败注册也做最佳努力清理。应用 context 注册避免服务最终清理与异步注销竞争，注销在 IO 执行。广播回调用不可变 profile 快照读取凭据，避免等正在执行平台调用的配置锁；消费后在 IO 重查原 socket/profile/AACP 再恢复媒体。

## 等待首个音频 profile 回调的资源与请求合并（续轮）

上一轮已把交付代理后的操作/释放移至 IO，但 `getProfileProxy` 的等待监听器仍直接保留服务和操作闭包，重复请求分别申请代理。本轮加入按 A2DP/HEADSET 分槽的 `PendingProfileRequests`：每个 profile 同时只有一个申请/执行槽，每个已知目的只保留最新待办；DISCOVER、SDP、ATTACH、PAUSE 和 POLICY 分开，普通查询不会覆盖连接策略操作。连接与释放策略共用 POLICY，配合原有归属票据，仅执行当前期望的操作。不同目的按首次入队顺序运行，重复目的替换值，不追加长度。执行中收到的新待办在当前代理完成释放后再申请下一代理。

框架监听器改为静态嵌套类，只持有 adapter、无操作闭包的票据、服务弱引用和已交付代理弱引用；没有隐式 `this$0`。服务资源关闭时清空整个待办表。首次回调晚到且服务已停止或已回收时，独立 IO 清理交付代理。重复交付同一代理不会另起操作，也不会提前关闭正在使用的代理。每个待办继续验证原服务代际，查询返回后再次检查；一个目的的异常不阻止同批其他有效目的。

## 头部追踪命令队列、采样门禁与旧恢复隔离（续轮）

页面和手势检测器原先同步调用 `sendDataPacket` 启停头部追踪，直接等待蓝牙输出锁；停止检测器还会回调服务，导致服务一次停止可能递归发送两包。本轮以 `HeadTrackingSession` 标记每次启停，`KeyedWorkSession` 只保留一个待办的最新状态。启停入口不再等待蓝牙输出锁；包构造及输出在 IO 执行。停止检测器的反馈音频清理仍沿用既有路径，没有据此证明全部主线程平台调用都已移出。停止立即使旧启停票据失效并清除采样许可，调用检测器停止时使用 doNotStop，避免递归追加停止命令。

## 蓝牙策略事务与主线程状态更新分离（续轮）

`withCurrent` 之前把归属对象的监视器持有到查询、setConnectionPolicy 或 connect 返回。这些操作已在 IO，但主线程的 select、revoke、beginRestore 和服务销毁仍可能等待同一个监视器。本轮用单独的策略锁排序平台动作，归属监视器只更新小规模状态，查询及平台调用不占用它。操作进入和返回后检查原票据；已发出的系统调用不能撤回，过期结果不继续连接、注册播放或授权新耳机。

不能仅拆掉锁后丢弃所有旧结果：耳机刚戴回时，已进入的释放策略可能仍会成功设为 FORBIDDEN。现在只在即将写策略时登记该 profile 的在途释放，查询阶段不登记。恢复请求可捕获这份待办，但执行时必须等释放结果确认：接受才授予恢复，拒绝或异常不设置 ALLOWED，也不调用 connect。额外的授权代际隔离选择变化、失去归属、手动连接和服务关闭；旧耳机即使随后被重新选择，迟到成功也不能借用新归属。控制 socket 单独掉线仍保留实际接受的释放，以便该耳机重连后修复策略。待办键仅有两种既有音频 profile，并在结果或授权撤销时清除。

如果释放失败，用户重新戴回时仍可能需要恢复已暂停的本地媒体。恢复回调只查询现有连接，确认当前票据、原 socket、服务及连接均有效后发送播放；不授予重连权限，不连接其他耳机。查询返回后再次检查，过期或未连接不会重启播放。媒体操作位于策略锁之外，沿用既有媒体控制锁的顺序。

## 连接通知后台发布与跨服务清理续轮

连接通知原先持有服务对象锁构建 PendingIntent 并同步调用 NotificationManager.notify/cancel。其他线程刷新通知时，Main 的名称偏好回调也要等待同一服务锁。现在通知构建及系统通知 IPC 交给进程内同一个串行 IO 槽位，只保留最新一条待办；每个服务持有一份归属租约，正常断开清除但不新建租约，避免反复断开增加资源记录。服务内锁仍保留输入顺序和断开状态处理，通知 IPC 不在这把锁内。首次前台服务通知仍立即创建，断开时的状态重置、历史 flush 和其他广播路径未全部后台化。

## 对话音量读取、渐变与退出恢复的 IO 串行化（2026-10-07）
